# Project instructions — Event-Driven GitHub Automation Bot

These are the standing instructions for any AI assistant (and human) working in this
repository. Read `docs/ARCHITECTURE.md` before changing structure.

## Working rules

- Inspect before modifying: read the files you are about to change and their callers.
- Preserve the existing architecture (see below). Propose changes before making
  structural ones.
- Do not invent APIs. For Next.js, read `node_modules/next/dist/docs/` (Next 16 — async
  `cookies()`/`headers()`/`params`, `proxy.ts` instead of middleware, no `next lint`).
  For GitHub, Slack, Neon, Vercel and Gemini, check the official documentation when
  behaviour matters.
- After every change: `npm run typecheck`, `npm run lint`, `npm test`. Fix failures before
  moving on. Run `npm run build` before declaring a phase done.
- Never fake an integration result. If GitHub/Slack/AI calls fail, the failure is recorded
  and shown; nothing reports success that did not happen.
- Do not add dependencies or services without a concrete need.
- Keep `AI_NOTES.md` factual: only record what actually happened.

## Architecture (do not change without discussion)

- One Next.js App Router app deployed on Vercel. API = Route Handlers in
  `src/app/api/**/route.ts` (Node.js runtime). Route handlers stay thin; logic lives in
  `src/server/**` and must be testable without Next.js.
- PostgreSQL (Neon) via Drizzle ORM + `pg`. Schema in `src/server/db/schema.ts`,
  migrations in `drizzle/` generated by drizzle-kit. Never edit applied migrations.
- Background work uses the Postgres `jobs` table (transactional outbox). Jobs are claimed
  with `FOR UPDATE SKIP LOCKED` + a lease. No in-memory queues, no fire-and-forget
  promises outside `after()`.
- The webhook route persists the event and its job in one transaction, responds, then
  drains jobs in `after()`.

## Security rules

- Never commit secrets. `.env` is git-ignored; `.env.example` holds names only.
- Never send secrets or GitHub tokens to the browser. No `NEXT_PUBLIC_` variable may hold a
  secret. Server-only modules import `server-only`.
- Never log secrets, tokens, Slack webhook URLs, cookies or full webhook payloads. Use the
  structured logger in `src/server/logger.ts`, which redacts known secret keys.
- Webhook signatures are verified over the raw body with a timing-safe comparison before
  anything else happens.
- Every query for user-owned data filters by the session user's id. Never trust an id from
  the client without an ownership check. Return 404 (not 403) for resources owned by others.
- Validate all input (body, query, params) with Zod at the route boundary.
- Client-facing errors are generic; details go to server logs.
- GitHub OAuth tokens and user Slack webhook URLs are encrypted at rest (AES-256-GCM).

## Coding conventions

- TypeScript strict mode. No `any` unless unavoidable and commented.
- Prefer small pure functions; side effects at the edges.
- Names: `camelCase` for code, `snake_case` for database columns.
- Errors: throw typed errors (`AppError`, `GitHubApiError`, ...); never swallow errors
  silently — either handle them meaningfully or log and rethrow.
- Comments explain _why_, not _what_.
- Formatting: Prettier (`npm run format`).

## API conventions

- JSON in, JSON out. Errors: `{ "error": { "code": string, "message": string } }`.
- Status codes: 400 validation, 401 unauthenticated, 404 not found / not owned,
  409 conflict, 429 rate limited, 500 unexpected.
- Mutating requests (POST/PATCH/DELETE) require a valid session and a same-origin
  `Origin` header, except the webhook and cron endpoints which use their own secrets.

## Database rules

- Schema changes: edit `schema.ts`, run `npm run db:generate`, review the SQL, commit it.
- Use constraints for invariants (`UNIQUE(delivery_id)`, `UNIQUE(webhook_event_id, rule_id)`),
  not application checks alone.
- Use transactions when writing related rows.
- No raw string interpolation into SQL; use Drizzle or the `sql` template tag.

## Testing rules

- Vitest. DB-backed tests run against PGlite (in-process Postgres) with the real
  migrations; no external services are called in tests — `fetch` to GitHub/Slack/Gemini
  is mocked.
- Every bug fix gets a regression test.
- Test security properties explicitly (forged signature, cross-user access, duplicates).

## Git rules

- Small, meaningful commits (`feat:`, `fix:`, `test:`, `docs:`, `chore:`).
- Check `git status` and `git diff` before committing; never commit `.env*` (except
  `.env.example`), `node_modules`, `.next`, or `coverage`.

## Deployment considerations

- Vercel Hobby: functions up to 300s; cron only once per day. The frequent sweeper is a
  GitHub Actions scheduled workflow calling `/api/cron/worker` with `CRON_SECRET`.
- `APP_URL` must be the public HTTPS origin in production; it is used for the OAuth
  callback and the webhook URL registered on GitHub.
- Apply migrations to Neon with `npm run db:migrate` before deploying code that needs them.
